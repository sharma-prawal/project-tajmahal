# Development guidelines & conventions

## Imports

Use the path aliases configured in `tsconfig.app.json` / `vite.config.ts`
instead of relative `../../../` chains:

```
@/*          -> src/*
@core/*      -> src/core/*
@narrative/* -> src/narrative/*
@player/*    -> src/player/*
@components/* -> src/components/*
@hooks/*     -> src/hooks/*
@state/*     -> src/state/*
@config/*    -> src/config/*
@constants/* -> src/constants/*
@utils/*     -> src/utils/*
@types/*     -> src/types/*
@assets/*    -> src/assets/*
```

Content-pipeline scripts (`scripts/content-pipeline/`) are a separate
TypeScript program (own `tsconfig.scripts.json`, run via `tsx`, checked by
`pnpm typecheck`) and do not use these aliases — they use relative imports
plus `.ts` extensions (`allowImportingTsExtensions`), since they run outside
Vite's resolver.

## Component rules

- One component's concern per file. If a file starts doing input handling
  *and* rendering *and* physics, split it — `PlayerController` is the one
  deliberate exception because those three things must stay in lockstep
  inside a single `useFrame`.
- No inline magic numbers for anything tunable (speed, sensitivity, FOV,
  fog distance, etc.) — add it to `constants/`.
- Avoid `useState` for anything that changes every frame (position,
  velocity, look deltas). Use `useRef` and mutate directly, or push into a
  Zustand store only if other components genuinely need to react to it.
- Keep components that render inside `<Canvas>` (R3F elements) separate
  from components that render as DOM overlays — don't mix Three.js JSX and
  HTML JSX in the same component.

## State

- Prefer local refs over global state. Reach for Zustand only when two or
  more unrelated components need the same value.
- Keep stores small and named for what they hold, not for the feature that
  first needed them.
- For state that's written every frame (or every few physics steps) by one
  system and read occasionally by another *outside* React's render tree, use
  a **module-level mutable singleton** (`player/lastCheckpoint.ts`,
  `core/perf/perfSample.ts`) rather than a Zustand store or React state —
  the getter/setter pair is the whole API, and nothing subscribes to it for
  re-renders. Reach for Zustand instead as soon as a *component* needs to
  reactively re-render off the value.

## Performance

- Nothing in a `useFrame` callback should allocate per frame if avoidable —
  reuse `Vector3`/`Quaternion` instances via refs (see
  `ExplorationCameraRig`).
- Dev-only visuals (stats, physics debug) must be gated behind
  `env.enableDebugTools` and never shipped enabled by default.
- New meshes should default to primitive geometry until an asset pipeline
  exists — don't hand-author complex geometry in code.

## TypeScript

- `strict` is on; don't weaken it per-file. Fix the type, don't suppress it.
- Shared types go in `types/`; types used by exactly one module can live
  next to that module.

## Linting/formatting/testing

Run before committing:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm format
```

`pnpm lint` runs with `--max-warnings 0` — warnings block CI the same as
errors. If a lint rule is genuinely wrong for a specific line, disable it
inline with a comment explaining why, not at the project level.

## Pure logic vs. framework glue

Where a piece of logic can be expressed as plain functions on numbers/plain
objects (locomotion math, orbit geometry, damping, state-machine
transitions), write it that way in its own file and unit-test it directly —
see `player/motor.ts`, `core/camera/orbitMath.ts`, `utils/math.ts`. Keep the
React/R3F/Rapier component as a thin adapter that calls the pure function
and applies the result (`setLinvel`, `camera.position`, etc.). This is what
makes locomotion and camera behavior testable without a WebGL context, and
is the pattern to follow for new gameplay math rather than inlining it into
a `useFrame`/`useBeforePhysicsStep` callback.

## Zustand `subscribe` diffing gotcha

A store method that reads via `get()` (e.g. `completedIds: () =>
deriveCompletedIds(get().phases)`) always reflects the **live** store, no
matter which snapshot object you call it on. If you `subscribe((state,
prevState) => …)` and call `state.completedIds()` vs.
`prevState.completedIds()` to diff before/after, both calls return the same
(current) answer — the diff silently does nothing. Instead, export a pure
function that takes the raw field (`deriveCompletedIds(phases)`) and call it
on `state.phases` and `prevState.phases` directly (see
`core/save/useAutoSave.ts`). This applies to any derived-getter pattern, not
just this one store.

## Content pipeline & dummy assets

`content/dummy/` fixtures (generated by
`scripts/content-pipeline/generate-dummy-assets.ts`) exist only to prove the
manifest/credits/content-lint pipeline works end-to-end — they are never
imported by app code and must never be treated as production placeholders.
If a pipeline check needs new coverage, extend `content-lint.ts` and, if a
new fixture type is needed, add it to the generator with the same "hand-
built, no external asset, clearly marked" standard as the existing ones —
don't download or generate anything that could pass for real content.

## Adding a new system

1. Does it belong under `core/` (engine-level, content-agnostic) or is it
   gameplay/content (`player/`, `components/`)? See ARCHITECTURE.md.
2. Add constants to `constants/`, not inline.
3. If it needs cross-component state, add a focused Zustand store.
4. If it's dev-only tooling, gate it behind `env.enableDebugTools` and put
   it in `components/dev/`.
